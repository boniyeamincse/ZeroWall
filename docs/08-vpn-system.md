## VPN Overview

ZeroWall supports three VPN protocols:

| Protocol | Best For | Crypto | NAT Traversal | Mobile Support |
|----------|---------|--------|--------------|---------------|
| WireGuard | Modern clients, performance | ChaCha20-Poly1305 | Yes (UDP) | Excellent |
| OpenVPN | Legacy clients, complex auth | AES-256-GCM | Yes (TCP/UDP) | Good |
| IPsec | Router-to-router, standards compliance | AES-256-GCM + SHA-256 | NAT-T | Variable |

## WireGuard

### How WireGuard Works

WireGuard operates at the **Layer 3** level, creating a virtual network interface (`wg0`, `wg1`, etc.) that routes packets over UDP. It uses a handshake based on the **Noise Protocol Framework** with **Curve25519** key exchange.

```
WireGuard Handshake (simplified):

Initiator (Client)              Responder (Server)
       │                               │
       │─── Initiation message ───────►│
       │    (Curve25519 ECDH +         │
       │     ephemeral key +           │
       │     MAC)                      │
       │                               │
       │◄── Response message ─────────│
       │    (Ephemeral key +           │
       │     session keys derived)     │
       │                               │
       │══════ Encrypted data ════════►│
       │◄════ Encrypted data ══════════│
       
Keys rotate every 3 minutes (180s) via rekey mechanism.
```

### Key Management

```sh
# Generate server key pair
wg genkey | tee /etc/zerowall/wg/server_private.key | wg pubkey > /etc/zerowall/wg/server_public.key

# Generate client key pair
wg genkey | tee client_private.key | wg pubkey > client_public.key

# Generate optional pre-shared key (hybrid PQ security)
wg genpsk > preshared.key
```

### Server Configuration

Via web UI: VPN > WireGuard > Add Server

```ini
# Generated /etc/wireguard/wg0.conf
[Interface]
PrivateKey = <BASE64_SERVER_PRIVATE_KEY>
ListenPort = 51820

# Peer: alice-laptop
[Peer]
PublicKey    = <ALICE_PUBLIC_KEY>
PresharedKey = <ALICE_PSK>
AllowedIPs   = 10.200.0.2/32

# Peer: bob-phone  
[Peer]
PublicKey    = <BOB_PUBLIC_KEY>
AllowedIPs   = 10.200.0.3/32

# Peer: branch-office-gw
[Peer]
PublicKey    = <BRANCH_PUBLIC_KEY>
Endpoint     = branch.example.com:51820
AllowedIPs   = 10.200.0.10/32, 192.168.2.0/24
PersistentKeepalive = 25
```

### Client Configuration (auto-generated by ZeroWall)

```ini
[Interface]
PrivateKey = <CLIENT_PRIVATE_KEY>
Address    = 10.200.0.2/32
DNS        = 192.168.1.1

[Peer]
PublicKey    = <SERVER_PUBLIC_KEY>
PresharedKey = <CLIENT_PSK>
Endpoint     = vpn.example.com:51820
AllowedIPs   = 0.0.0.0/0   # Full tunnel
# AllowedIPs = 192.168.1.0/24, 192.168.2.0/24  # Split tunnel
PersistentKeepalive = 25
```

ZeroWall exports client configs as QR code (for mobile) or `.conf` file download.

### WireGuard Firewall Integration

ZeroWall automatically creates pf rules for WireGuard:

```pf
# Allow WireGuard handshake on WAN
pass in on $WAN proto udp to ($WAN) port 51820 keep state

# Route VPN clients to LAN
pass in on wg0 from 10.200.0.0/24 to 192.168.1.0/24
pass out on $LAN from 10.200.0.0/24 to 192.168.1.0/24

# Outbound NAT for VPN clients to internet
nat on $WAN from 10.200.0.0/24 to any -> ($WAN)
```

## OpenVPN

### Architecture

OpenVPN operates in **userspace** using TUN (routed Layer 3) or TAP (bridged Layer 2) interfaces. TUN mode is recommended for most deployments.

```
OpenVPN Connection Flow:

Client                           Server (ZeroWall)
  │                                    │
  │──── TLS ClientHello ──────────────►│
  │◄─── TLS ServerHello + Cert ────────│
  │──── Client Cert (mutual TLS) ─────►│
  │◄─── TLS Handshake Complete ────────│
  │                                    │
  │════ Encrypted tunnel established ══│
  │                                    │
  │  Server pushes:                    │
  │  - Assigned IP (e.g., 10.8.0.2)   │
  │  - Routes to push                  │
  │  - DNS server                      │
```

### Server Configuration Options

| Option | Default | Notes |
|--------|---------|-------|
| Protocol | UDP | TCP available (for restrictive networks) |
| Port | 1194 | Configurable |
| Cipher | AES-256-GCM | Required TLS 1.2+ |
| Auth | SHA256 | HMAC digest |
| Topology | subnet | Recommended over net30 |
| TLS Auth | Enabled | Pre-shared HMAC key prevents port scans |

### Authentication Modes

```
Mode 1: Certificate only (mutual TLS)
  Client presents certificate signed by ZeroWall CA

Mode 2: Certificate + Password
  Certificate required AND username/password
  Password verified against local user DB or LDAP/RADIUS

Mode 3: Certificate + Password + TOTP
  Full MFA — recommended for sensitive environments
```

### LDAP/RADIUS Integration

```xml
<!-- LDAP auth plugin config (in config.xml) -->
<openvpn_server>
  <auth_mode>ldap+cert</auth_mode>
  <ldap>
    <server>ldap://dc.corp.example.com</server>
    <base_dn>DC=corp,DC=example,DC=com</base_dn>
    <bind_dn>CN=vpnbind,OU=Service,DC=corp,DC=example,DC=com</bind_dn>
    <user_attr>sAMAccountName</user_attr>
    <group_filter>(&(objectClass=group)(cn=VPN-Users))</group_filter>
  </ldap>
</openvpn_server>
```

## IPsec

### IKEv2 Configuration

IPsec with IKEv2 is the preferred standard for site-to-site connectivity with third-party routers (Cisco, Juniper, Palo Alto, etc.).

```
Phase 1 (IKE SA) — Authentication & key exchange:
  - Encryption: AES-256-GCM
  - PRF: SHA-256
  - DH Group: 14 (2048-bit) or 19 (256-bit ECP)
  - Lifetime: 28800 seconds
  - Auth: PSK or certificates

Phase 2 (Child SA / IPsec SA) — Data encryption:
  - ESP encryption: AES-256-GCM
  - Lifetime: 3600 seconds
  - PFS: DH Group 14 or 19
```

### IPsec Site-to-Site Example

```
ZeroWall A (203.0.113.1)          ZeroWall B (198.51.100.1)
LAN: 192.168.1.0/24               LAN: 192.168.2.0/24

Phase 1:
  Local:  203.0.113.1
  Remote: 198.51.100.1
  Auth:   PSK "s3cr3t_psk_here"
  IKE:    AES256-SHA256-DH14

Phase 2:
  Local network:  192.168.1.0/24
  Remote network: 192.168.2.0/24
  ESP:            AES256GCM
  PFS:            DH Group 14
```

## Choosing a VPN Protocol

```
Decision tree:

Need to connect mobile users (phones/laptops)?
├── Yes → Prefer WireGuard (native clients on all OS)
│         OpenVPN if LDAP/AD auth required
└── No (site-to-site) →
    ├── Both ends are ZeroWall? → WireGuard (simpler, faster)
    └── Third-party router? → IPsec IKEv2 (standards-based)
    
Need TCP fallback for restrictive firewalls? → OpenVPN TCP mode
Performance is critical? → WireGuard (kernel-native)
Compliance requires IPsec/IKEv2? → IPsec
```

## Road Warrior Configuration

A "road warrior" VPN allows mobile users to connect from any internet location.

### WireGuard Road Warrior Setup

1. Navigate to VPN > WireGuard > Servers > Add
2. Set interface address (e.g., `10.200.0.1/24`)
3. Set listen port (`51820`)
4. Navigate to Peers > Add for each client:
   - Enter client's public key
   - Assign IP from tunnel subnet (e.g., `10.200.0.2/32`)
5. Save and Apply
6. Export client config (QR or file)

### OpenVPN Road Warrior Setup

1. Navigate to VPN > OpenVPN > Servers > Add
2. Set mode: Remote Access (SSL/TLS + User Auth)
3. Configure CA and server certificate
4. Set tunnel network (e.g., `10.8.0.0/24`)
5. Set DNS server and push routes
6. Create user certificates under System > Certificates
7. Export client bundle (`.ovpn` file with embedded certs)

## Site-to-Site VPN

### WireGuard Site-to-Site

Requires ZeroWall at both sites. Each site's ZeroWall acts as both a WireGuard server and peer.

```
Site A ZeroWall                    Site B ZeroWall
wg0: 10.10.10.1/30                wg0: 10.10.10.2/30
LAN: 192.168.1.0/24               LAN: 192.168.2.0/24
Public: 203.0.113.1               Public: 198.51.100.1

Site A wg0.conf [Peer] section:
  PublicKey    = <SiteB_pubkey>
  Endpoint     = 198.51.100.1:51820
  AllowedIPs   = 10.10.10.2/32, 192.168.2.0/24

Site B wg0.conf [Peer] section:
  PublicKey    = <SiteA_pubkey>
  Endpoint     = 203.0.113.1:51820
  AllowedIPs   = 10.10.10.1/32, 192.168.1.0/24
```

## VPN Routing & Split Tunneling

### Full Tunnel
All client traffic routed through VPN (including internet):
```ini
# WireGuard client
AllowedIPs = 0.0.0.0/0, ::/0
```

### Split Tunnel
Only traffic destined for corporate networks goes through VPN; internet traffic uses local connection:
```ini
# WireGuard client
AllowedIPs = 192.168.1.0/24, 192.168.2.0/24, 10.0.0.0/8
```

### DNS Routing with Split Tunnel

ZeroWall pushes its DNS server to VPN clients:
- WireGuard: `DNS = 192.168.1.1` in client config
- OpenVPN: `push "dhcp-option DNS 192.168.1.1"`

Unbound handles internal name resolution; external names forwarded to upstream.

## Multi-VPN & Redundancy

### Dual VPN Endpoints (Failover)

```
Primary VPN:   vpn1.example.com:51820 (WireGuard, 100Mbps link)
Failover VPN:  vpn2.example.com:51820 (WireGuard, 50Mbps backup link)
```

WireGuard clients can be configured with multiple endpoints; ZeroWall monitors tunnel health and re-routes via the secondary if the primary fails.

### VPN + HA (High Availability)

With a CARP HA pair, VPN endpoints bind to the CARP VIP. On failover, the secondary ZeroWall takes over the VIP and VPN sessions reconnect automatically (WireGuard reconnect is near-instantaneous; OpenVPN clients reconnect within seconds).

## VPN Troubleshooting

### WireGuard Diagnostics

```sh
# Show current WireGuard status (peers, handshakes, traffic)
wg show

# Check if tunnel interface is up
ifconfig wg0

# Verify routing
netstat -rn | grep 10.200

# Ping through tunnel
ping -S 10.200.0.1 10.200.0.2

# Check firewall rules
pfctl -sr | grep 51820
```

### OpenVPN Diagnostics

```sh
# Check OpenVPN status
cat /var/log/openvpn/server-1-status.log

# Watch OpenVPN log in real time
tail -f /var/log/openvpn/server-1.log

# List connected clients
cat /var/db/zerowall/openvpn/server-1-status.log
```

### Common Issues

| Issue | Symptoms | Solution |
|-------|---------|---------|
| NAT traversal failure | Handshake fails behind double NAT | Enable PersistentKeepalive = 25 |
| MTU mismatch | Large packets dropped, small packets work | Set MTU 1380 on WG interface |
| DNS leak | Resolving via ISP instead of VPN DNS | Set DNS in client config, block port 53 on non-VPN interfaces |
| Routing conflict | VPN up but can't reach hosts | Check AllowedIPs covers destination subnet |
| Clock skew | WireGuard handshake rejected | Ensure NTP sync on both ends |
